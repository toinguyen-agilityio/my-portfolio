# QA release report

Turns the results of a release test pass into one self-contained HTML page that a PO or reviewer can read without opening GitHub. The page is generated by a script from a JSON file, so every report looks the same and you only write the content.

What the reader gets:

- A sidebar agenda: issues as small grey group labels, test cases as large links. Failed cases are red. On narrow screens it becomes a drawer.
- A failure banner, then summary counts, then one collapsible block per issue (Expand all / Collapse all).
- Each test case in this order: **title → what is tested → expected → actual result** (pass/fail, with one bullet per finding and links such as "Shot 3 Shot 6" to the screenshots that prove it) **→ raw test output (collapsed) → numbered screenshots**.
- Clicking a screenshot opens a viewer with prev/next, arrow keys, zoom and Esc.
- An EN/VI toggle when the report is bilingual.

## Steps

### 1. Collect the results

The report only shows evidence from this session. If the tests have not been run yet, run them first (in this repo, follow `.claude/agents/qa-agent.md` and `.claude/references/qa-agent/test-plan.md`: production build, Playwright, light and dark, 320/375/1280).

For each issue in the release, collect its test cases. For each case you need: what you did, what the ticket says should happen, what actually happened, the raw lines your script logged, and the screenshots.

Name screenshots `<case-id>-<what>-<light|dark>-<width>.png` (for example `98-4-travel-dark-375.png`): the caption ("dark · 375px") is read from the name. Capture at `deviceScaleFactor: 1`. Prefer viewport shots or element shots for desktop widths over full-page shots, because full-page desktop shots are hard to read when scaled into the grid. If the total size will pass ~15 MB, save as JPEG (`type: 'jpeg', quality: 80`).

### 2. Write report.json

**Look at the example first.** [examples/release-1/report.json](examples/release-1/report.json) is the real Release 1 report (5 issues, 29 cases, 1 failure, bilingual), the one the user signed off. Copy its tone and level of detail: how `tested`, `expected` and `result` are phrased, how findings point to shots, how the failed case 105-1 explains the cause and the decision needed, how #101 and #102 share one block, and what goes in `extra` and `notCovered`. Its screenshots are not in the repo; to see how it renders, build it with `--skip-missing`, which draws grey placeholders:

```bash
node .claude/skills/my-qa-release-report/scripts/build-report.mjs .claude/skills/my-qa-release-report/examples/release-1/report.json --out /tmp/example.html --skip-missing
```

Use the example for style, never for content: every line of a new report comes from the tests you ran.


Then put your own `report.json` next to a `shots/` folder in a scratch directory outside the repo tree (the evidence itself goes to the evidence branch, see the QA agent). The format is in [references/report-json.md](references/report-json.md). Read it before writing the file.

How to write the content well:

- **One case = one thing a reviewer would tick off.** Split a case when its findings need different screenshots to prove them.
- **`tested`** names the pages, widths, themes and actions. **`expected`** comes from the ticket's acceptance criteria, not from what you saw.
- **`result`** is one sentence that starts with "Matches:" or "Does not match:". The detail goes in `findings`.
- **Every finding points to the screenshots that prove it.** This is the whole point of the page: a reviewer must never have to guess which of 14 screenshots shows the bug. For a failure, point to the shot where the defect is most visible (usually the desktop shot that shows all items side by side), and add a separate finding for what still passed.
- A failed finding says what is wrong and where it comes from (file, field, component), and what decision is needed (file a bug, or confirm the behaviour is intended).
- Never mark something pass that you did not check. Things only a person can do (real Safari, real phones, visual "no flash") go in `notCovered`.
- Sort issues by issue number. When two issues were tested together, make one block with `label: "#101 and #102"`.
- If the user writes in Vietnamese, make the report bilingual (`"languages": ["en", "vi"]`) and write both texts; keep `raw` as logged.

### 3. Build

```bash
node .claude/skills/my-qa-release-report/scripts/build-report.mjs <dir>/report.json --out <dir>/report.html
```

The script embeds every screenshot, computes all counts and the failure banner, and checks the file. Never use `--skip-missing` for a real report. Fix every error it prints (a missing file, a finding that points to a shot that does not exist). Treat warnings about unreferenced screenshots seriously: either point a finding at the shot or drop it.

### 4. Check it in a browser

Open `report.html` with Playwright and look at it yourself before you hand it over:

- Screenshot the top of the page and one failed case, in both languages if bilingual.
- Click a sidebar link, a "Shot n" link and a screenshot (the viewer must open), and check there are no page errors.

### 5. Publish

- If the Artifact tool is available (`mcp__claude-artifacts__*`), publish `report.html` as an artifact with `publish_files` and give the user the link. To update an existing report, republish to the same artifact with its current `base_version`.
- Otherwise give the user the HTML file. In this repo, the QA evidence comment can link to it on the evidence branch.

Tell the user the result in two or three sentences: pass/fail counts, the failed cases, and what is left for a person.

## Changing the design

The look and behaviour live in `assets/report.css` and `assets/report.js`; the markup is in `scripts/build-report.mjs`. Change them there, not in a generated report, so the next report keeps the change. Rebuild a report and check it in a browser after any change.
